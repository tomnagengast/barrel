**Short answer: Markdown is fine as the storage format, but QMD doesn't add much here. The issue isn't the format — it's the lack of structured metadata.**

Here's my reasoning:

**QMD (Quarto) doesn't buy you much because:**
- QMD's value is executable code cells and rendering pipelines — you're not running code in your prompt logs
- Its YAML-header-per-cell approach doesn't map well to conversation turns
- It adds a Quarto dependency for parsing, when your prompt logs are a simple structure

**What actually matters for efficient parsing of prompt history:**

1. **Structured metadata** — The stats are trapped in a markdown table, which is annoying to parse. Timestamps are in heading text. Tool breakdowns are comma-separated strings.

2. **Machine-parseable turn boundaries** — The `## TIMESTAMP` / `### Prompt` / `### Response` convention works but relies on heading-level parsing.

3. **Searchability** — Finding "all turns that wrote to file X" or "all turns with >5 tool errors" requires parsing those markdown tables.

**My recommendation: add YAML front matter + keep markdown body.** Two small changes to the hooks would make retrospective parsing trivial:

1. Add a YAML front matter block to each session file with session-level metadata
2. Use a structured delimiter for each turn (e.g., a YAML block between turns) so you can parse stats without table-scraping

Something like:

```markdown
---
session_id: abc123
started: 2026-02-15T17:12:44
project: barrel
branch: claude/markdown-editor-plan-OZ0tV
---

## 20260215_171244

### Prompt

<text>

### Response

<text>

### Stats

duration: 45s
tool_calls: 12
tools: {Read: 4, Edit: 3, Bash: 5}
errors: 0
files_read: [a.swift, b.swift]
files_written: [c.swift]
subagents: 2
-->
```

The `<!-- turn-meta ... -->` block gives you a YAML-parseable structure inside an HTML comment (invisible when rendered as markdown, trivial to extract with regex or a simple parser). This keeps the files fully readable as plain markdown while making programmatic extraction a one-liner.

That changes the question entirely. QMD isn't a file format — it's a **local search engine** for indexing and querying markdown documents. So the real question is: is your current markdown prompt log structure good enough for QMD to index and retrieve effectively during retrospectives?

**Yes, markdown is the right format — QMD is designed to consume it.** The question becomes whether your current log *structure* is optimal for QMD's retrieval pipeline. A few observations:

**What works well already:**
- One file per session in `prompts/` — QMD can index a collection with a glob like `prompts/*.md`
- Plain markdown with headings — BM25 full-text search will find keyword matches easily
- Human-readable text — the semantic/vector search will embed prompt and response content naturally

**What could improve retrieval quality:**
1. **Collection context** — QMD lets you add descriptive context to collections. Setting context like "Claude Code session logs containing user prompts, assistant responses, tool usage stats, and subagent summaries for a macOS markdown editor project" would significantly improve query expansion and re-ranking.

2. **The stats tables are noise for semantic search** — lines like `| Tool calls | 4 |` and `| Duration | 2m 40s |` will dilute embeddings. QMD's vector search would benefit if stats were either in a separate file or clearly demarcated so they don't muddy the semantic signal of the actual prompt/response content.

3. **Turn-level headings could be richer** — `## 20260215_190351` is just a timestamp. If the prompt hook also wrote a brief topic slug (even just the first ~60 chars of the prompt), QMD's BM25 and semantic search would match on section headings better.
