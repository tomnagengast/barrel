> Here’s how I’d approach the design:
> 
> Core Philosophy
> 
> Carmack’s approach boils down to: do the simplest thing that could work, measure everything, eliminate waste. For a markdown editor that means minimizing layers of abstraction, avoiding frameworks that hide allocation patterns, and keeping the hot path (keystroke → re-parse → re-render) as tight as possible.
> 
> Key Architectural Decisions
> 
> Language: Swift + AppKit (not SwiftUI)
> 
> SwiftUI’s declarative diffing is antithetical to the goal here. AppKit gives you direct control over the text system, and NSTextView is battle-tested for text editing. Swift gives you value types to avoid heap allocations on the hot path and easy interop with C libraries. No Electron, no WebView for rendering.
> 
> Parsing: cmark-gfm (C library) with incremental strategy
> 
> Don’t write your own parser — cmark is a state machine in C, it’s extremely fast, and it’s CommonMark-compliant. The real performance trick is incremental parsing: on each edit, only re-parse the affected block-level node (paragraph, list, code block), not the entire document. cmark’s AST makes this feasible — you track which byte ranges map to which AST nodes, and on edit you invalidate/re-parse only the dirty range plus surrounding context.
> 
> Text System: Custom NSTextStorage subclass
> 
> This is where the Carmack energy lives. NSTextStorage is the backbone of Cocoa’s text system. By subclassing it, you intercept every edit and can:
> 
> ∙ Trigger incremental re-parse of only the changed region
> 
> ∙ Apply syntax highlighting as attributed string changes in-place (no full re-render)
> 
> ∙ Keep a parallel data structure mapping document ranges → cmark AST nodes
> 
> Rendering: NSTextView + NSLayoutManager (TextKit 1, not TextKit 2)
> 
> TextKit 2 is still buggy and less predictable. TextKit 1’s NSLayoutManager gives you fine-grained control over glyph generation and layout. For the preview pane (if you want one), render to NSAttributedString from the cmark AST — no WebView.
> 
> File I/O: Memory-mapped files
> 
> Use mmap for large files. No reason to read an entire 10MB markdown file into a heap buffer. The OS virtual memory system handles paging for free. For saves, use atomic writes (Data.write(to:options:.atomic)).

> Component Breakdown
> 
> 1. Document Model — A rope or gap buffer backing the raw text. Swift’s String is fine for moderate files, but for truly large files a rope data structure (tree of string chunks) gives you O(log n) insertions. Start with String, profile, upgrade if needed.
> 
> 2. Block Map — An interval tree or sorted array mapping byte ranges to cmark AST block nodes. On edit, binary search to find affected blocks, mark dirty, re-parse only those.
> 
> 3. Syntax Highlighter — Walks the cmark AST and maps node types to NSAttributedString attributes. Operates only on dirty ranges. No regex-based highlighting — the AST already tells you what everything is.
> 
> 4. Preview Renderer (optional) — If you want a side-by-side preview, render from cmark AST → NSAttributedString in a second NSTextView (read-only). Not a WebView. This shares the same AST, so no double-parsing.

Below is a concrete plan that stays macOS-only, keeps the hot path tight, and gives you room to scale from “works” to “absurdly fast” without rewriting everything.

  

  

What you are building

  

  

A native macOS Markdown editor with a live preview that stays responsive under big files and high typing rates.

  

Core behaviors:

  

- Fast source editing (never block the main thread on parsing or preview work)
- Live preview that updates incrementally (do as little work as possible per edit)
- Minimal memory churn (avoid rebuilding whole strings, whole attributed strings, or whole layouts)

  

  

Scope guardrails for v1:

  

- Single file, single window
- CommonMark plus a small explicit extension set (pick a short list and treat everything else as plain text)
- No WebView, no HTML render loop
- No plugin system, no “workspace” or vault management

  

  

  

Architectural principles

  

  

Non-negotiable invariants:

  

1. Keystroke path stays lean: editing must remain smooth even if preview lags.
2. Incremental by default: edits only invalidate a small region, and only that region gets reparsed and rerendered.
3. Cache everything with stable IDs: blocks keep identities across edits so you reuse layout and rendering.
4. Measure from day 1: you cannot optimize what you do not track.

  

  

  

Recommended stack

  

  

  

UI

  

  

- AppKit
- Editor: NSTextView with minimal attributes (keep source view mostly plain).
- Preview: start with a second read-only text view for speed of implementation, then graduate to a custom tiled CoreText view if needed.

  

  

Text system choice:

  

- Start with TextKit 1 (NSTextView + NSLayoutManager) for predictability and fine control over invalidation.
- Keep your design modular so you can experiment later without touching the core engine.

  

  

  

Parsing

  

  

Two viable strategies:

  

Path A (pragmatic, small dependency surface): cmark-gfm

  

- Pros: correctness, CommonMark/GFM semantics, fast C parser, stable.
- Cons: not inherently incremental, you implement incremental behavior by reparsing only a safe region.

  

  

Path B (incremental parsing out of the box): tree-sitter Markdown

  

- Pros: true incremental parse, gives you structural ranges cheaply.
- Cons: introduces a grammar dependency and you still need a semantic layer for rendering choices.

  

  

If you want the smallest moving parts first, go with cmark-gfm and implement “incremental enough” by region invalidation. If you strongly care about deep incremental structure from the start, go tree-sitter.

  

My suggestion:

  

- Start with cmark-gfm for correctness and early shipping.
- Design the core so the parser is a pluggable module. If later you hit a wall, you can swap in tree-sitter for structure while keeping the rest intact.

  

  

  

Core modules and data structures

  

  

Design this as a small engine with clean boundaries:

  

  

1) DocumentSnapshot

  

  

An immutable view used by background work.

  

- text: NSString (source of truth for v1)
- revision: Int (monotonic generation)
- lineIndex: LineIndex (newline offsets in UTF-16 units)

  

  

Why NSString and UTF-16 offsets:

  

- AppKit uses NSRange in UTF-16.
- Keeping offsets in the same coordinate system avoids constant expensive mapping.

  

  

  

2) LineIndex

  

  

Maintains line start offsets to make these operations fast:

  

- Expand an edit to whole lines
- Map “line, column” style positions if needed
- Find block boundaries by scanning lines near the edit

  

  

Implementation shape:

  

- [Int] lineStarts where each entry is a UTF-16 offset
- Incrementally update only the affected line range on edit (do not rescan the whole file)

  

  

  

3) DirtyTracker

  

  

Coalesces edits into a minimal set of invalid ranges:

  

- Merges overlapping and adjacent ranges
- Can grow a range to “safe reparse region” (more on that below)

  

  

  

4) BlockIndex

  

  

A flat array of block records, ordered by source range:

  

BlockRecord

  

- id: BlockID (stable identity)
- range: NSRange (source range in UTF-16)
- kind: BlockKind (heading, paragraph, list, code fence, quote, etc.)
- hash: UInt64 (hash of source slice + relevant style settings)
- layoutKey: LayoutKey (font size, width constraints, theme variant)

  

  

Stable IDs matter because they let you reuse cached layout even when offsets shift.

  

How to keep IDs stable:

  

- For unchanged blocks, preserve ID.
- For changed region, create new IDs only for blocks that truly changed content or kind.
- For moves caused by insertions above, keep IDs and just update ranges.

  

  

  

5) RenderCache

  

  

Caches per-block layout and draw artifacts:

  

- For NSTextView preview: cached NSAttributedString per block (or per paragraph).
- For CoreText preview: cached CTFramesetter or precomputed line breaks, plus measured height.

  

  

  

6) PreviewModel

  

  

A lightweight representation of what the preview needs:

  

- List of blocks with their attributed runs or layout handles
- Heights and y-offsets (prefix sums) for fast scrolling if using custom view

  

  

  

The edit to preview pipeline

  

  

  

Hot path (main thread)

  

  

On every edit:

  

1. NSTextStorage.processEditing() (or delegate callback)
2. Record editedRange and changeInLength into DirtyTracker
3. Update LineIndex incrementally for affected lines
4. Schedule background update with cancellation

  

  

Main thread must not:

  

- Parse Markdown
- Build large attributed strings
- Perform layout for the whole preview

  

  

  

Background path (coalesced, cancelable)

  

  

A worker job does:

  

1. Capture a DocumentSnapshot (text + revision + line index)
2. Compute safe reparse region from the dirty range
3. Parse only that region (or a slightly expanded region)
4. Build new blocks for that region and diff against existing BlockIndex
5. Build updated preview artifacts only for changed blocks
6. Dispatch a small “apply diff” back to the main thread, guarded by revision

  

  

  

Safe reparse region

  

  

Markdown is context sensitive around lists, indentation, and fenced blocks. The trick is to expand the dirty range to a region that is guaranteed to reparse correctly without reparsing the whole file.

  

A practical rule set that works well:

  

- Expand to full lines for the edit.
- Then expand upward and downward until you hit a “hard boundary”.
- Hard boundaries usually include:  
    

- Blank line that is not indented as part of a list/quote continuation
- Start or end of a fenced code block
- Heading line
- Horizontal rule line

-   
    
- Add a small safety margin of a few lines above and below.
- If your scan detects you are inside a fence, expand to the entire fence.

  

  

This is deliberately simple and measurable. You can tighten it later with profiling.

  

  

Preview rendering strategy

  

  

  

Stage 1 (fast to build): preview as read-only NSTextView

  

  

- Build attributed strings per changed block and splice them into the preview text storage.
- Do not rebuild preview for the entire document.
- Use minimal attributes:  
    

- Fonts and weights for headings
- Monospace for code
- Link attributes
- Paragraph styles for list indentation

-   
    

  

  

This will get you a working, native preview quickly and is surprisingly performant if you keep updates localized.

  

  

Stage 2 (max performance): custom preview view with CoreText and tiling

  

  

Use a custom NSView inside an NSScrollView:

  

- Preview is a list of blocks, each block can layout itself given a width.
- Only layout and draw blocks that are visible.
- Cache layout results keyed by (BlockID, width, theme).

  

  

This gives you:

  

- Very low memory overhead for huge docs
- Predictable scrolling performance
- No hidden relayout costs from TextKit

  

  

Graduation criteria:

  

- If preview NSTextView starts dropping frames while scrolling large files
- If attributed string memory becomes dominant
- If you need strict control over what gets laid out and when

  

  

  

File I/O and large file behavior

  

  

Open:

  

- For v1: Data(contentsOf:) plus decode to String is acceptable up to moderately large files.
- For large file mode: memory-map (mmap) and decode once.
- Build LineIndex in one pass.

  

  

Save:

  

- Atomic writes (write to temp, then replace).
- Avoid converting the whole document multiple times. Treat “export” and “save” as separate pipelines.

  

  

File watching:

  

- Use a file descriptor plus DispatchSource to detect external modifications.
- If file changed externally:  
    

- If your buffer is unmodified, reload
- If modified, show a minimal conflict prompt and offer: overwrite, reload, or diff (diff can be a later feature)

Here’s a seedable layout architecture that optimizes for extreme performance and for agentic development. It’s two things at once:

1. A runtime layout pipeline (parse → blocks → layout → draw) that is incremental, cacheable, and cancelable

2. A repo layout that gives agents strong backpressure, clear boundaries, and progressive disclosure

  

⸻

  

Layout engine architecture

  

The core idea

  

Treat Markdown preview as a list of independent blocks (paragraphs, headings, list items, code fences, quotes). Each block is:

• Identified by a stable BlockID

• Has a source NSRange in UTF-16 (to match AppKit)

• Can be laid out independently given a width constraint

• Can be cached independently

  

Then the preview view draws only the visible blocks and re-lays out only blocks affected by an edit.

  

This avoids the classic traps:

• Rebuilding a whole attributed string for the document

• Re-laying out everything on every keystroke

• Any HTML/WebView pipeline

  

Data model (minimal and explicit)

  

Parse output (semantic-ish)

• BlockModel

• id: BlockID

• kind: BlockKind (heading, paragraph, listItem, codeFence, quote, thematicBreak…)

• range: NSRange (source)

• inlines: [InlineSpan] (for paragraph/heading/list items)

• metadata: BlockMetadata (heading level, fence language tag, list depth, quote depth…)

  

Layout output (view-independent)

• LayoutBlock

• id: BlockID

• measuredHeight: CGFloat

• baselineMap / linkRects / hitTestData (enough for selection + click-to-jump)

• drawPayload: DrawPayload (backend-specific, see below)

• sourceRange: NSRange

  

Indexing

• BlockIndex

• ordered [BlockModel] by range.location

• supports binary search by source location

• stores a prefix-sum height table once blocks are laid out (for scrolling)

  

Pipeline stages (pure functions where possible)

1. Snapshot

  

• Capture DocumentSnapshot with:

• revision: Int

• text: NSString

• lineIndex: LineIndex (newline offsets in UTF-16)

• Snapshot is immutable and safe to process off-main.

  

2. Dirty region expansion

  

• Convert the edit range into a safe reparse region:

• Expand to full lines

• Expand to enclosing fence if inside a code fence

• Expand outward to nearest “hard boundaries” (blank line boundaries, headings, thematic breaks), plus a small safety margin

  

3. Parse

  

• Parse only that region (cmark-gfm or other parser module)

• Produce block candidates with ranges relative to the snapshot

  

4. Block diff

  

• Compare new blocks in region vs old blocks in region

• Preserve BlockIDs for unchanged blocks so caches survive inserts above

• Output:

• removedBlockIDs

• insertedBlocks

• updatedBlocks (same ID, changed content/metadata)

• rangeShiftDeltas (for blocks after the edit)

  

5. Layout

  

• For each inserted/updated block, compute LayoutBlock given:

• width constraint

• theme style set

• font metrics

• Cached by (BlockID, widthBucket, themeVariant, contentHash)

  

6. Render apply

  

• Main thread applies a minimal diff to the preview:

• update block list

• update height prefix sums

• invalidate visible rects for updated blocks only

  

Render backend (two-tier strategy)

  

Backend A: TextKit preview (fast to ship)

• Each block produces an NSAttributedString

• Preview is a read-only NSTextView, but you update it using block-level splices

• You still keep the block model and layout cache so you do not rebuild the world

  

Backend B: Custom CoreText preview (max control)

• A custom NSView inside NSScrollView

• Draws only visible blocks (tiled rendering)

• Each LayoutBlock.drawPayload stores CoreText layout objects (or your own line break results)

• Scroll stays smooth for huge docs because you never ask TextKit to hold the entire preview

  

Design the engine so both backends share the same BlockModel and LayoutBlock types. Switching backends later should touch only the preview module.

  

⸻

  

Concurrency, cancellation, and backpressure

  

This is where “don’t waste your backpressure” becomes a concrete design constraint: the system must generate fast, deterministic feedback and must not do pointless work when the user types quickly.  

  

A single coordinator with bounded work

  

Create a LayoutCoordinator (an actor is perfect in Swift):

  

Responsibilities:

• Accept edit events with (editedRange, delta, revision)

• Coalesce edits into a single dirty region

• Maintain “latest desired revision”

• Run background pipeline jobs

• Drop obsolete work automatically (last-write-wins)

  

Important behavior:

• If a new edit arrives, cancel the in-flight job.

• Never queue unbounded jobs.

• Keep only the newest snapshot and newest dirty region.

  

This avoids the lock-contention and shared-file bottlenecks Cursor saw when agents coordinated via locks.  

  

Two-phase commit to UI

  

Each background job computes PreviewDiff(revision: Int, changes: …).

Main thread applies it only if diff.revision == currentRevision.

  

No partial apply. No stale apply.

  

Explicit “quality backpressure” hooks

  

Make it cheap for agents (and humans) to know when a change is correct:

• scripts/check.sh runs:

• swiftformat (or equivalent)

• swiftlint (if you choose)

• unit tests

• Add a perf smoke test script that loads large fixtures and simulates edits

  

This aligns with:

• Cursor’s emphasis on verifiable goals and tests  

• HumanLayer’s point that you should not use the model as a linter, use deterministic tools and optionally hooks to feed failures back  

• Moss’s point that build tooling feedback prevents you from spending attention on trivial corrections
