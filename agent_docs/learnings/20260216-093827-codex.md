# Barrel Xcode Launch Debugging Learnings (2026-02-16)

## Summary
- Build warnings and Swift concurrency diagnostics were not the only issue; the bigger blocker was launch behavior under Xcode package schemes.
- The app binary itself was healthy when launched directly; most "no app shown" behavior came from scheme/run configuration and package-scheme launch wiring.

## Key Learnings

1. Swift 6 `Sendable` checks for Foundation reference types need explicit handling.
- `NSString` and `NSAttributedString` triggered Swift 6 mode diagnostics.
- Safe fix was to mark audited immutable containers as `@unchecked Sendable` with rationale comments:
  - `packages/MarkdownEngine/Sources/MarkdownCore/DocumentSnapshot.swift`
  - `packages/MarkdownEngine/Sources/MarkdownLayout/LayoutTypes.swift`

2. "Build succeeded, no app window" can be a scheme launch configuration bug, not an app crash.
- `MarkdownEngine-Package` may build all targets but still not run the intended executable unless `LaunchAction` has a `BuildableProductRunnable`.
- Adding explicit runnable target (`MarkdownApp`) to `MarkdownEngine-Package.xcscheme` removed ambiguity.

3. Relying on implicit app startup in SwiftPM can be fragile.
- Switched to explicit AppKit entry (`static main()`) that:
  - creates `NSApplication.shared`
  - assigns retained delegate
  - sets activation policy
  - calls `app.run()`
- This made delegate lifecycle deterministic and observable.

4. Window lifetime matters.
- Creating `EditorWindowController` as a local variable in `applicationDidFinishLaunching` risks immediate deallocation.
- Retaining it on `AppDelegate` fixed that class of "nothing appears" behavior.

5. Fast diagnostics that worked well.
- Added launch instrumentation (`print`, `NSLog`, `/tmp/barrel-launch.log`) in `AppDelegate`.
- Ran built binary directly from DerivedData to separate app correctness from Xcode scheme/debugger behavior.
- Confirmed process visibility/frontmost state with `osascript` and process liveness with `ps`.

## Scheme Hardening Applied
- Updated shared package scheme:
  - `packages/MarkdownEngine/.swiftpm/xcode/xcshareddata/xcschemes/MarkdownEngine-Package.xcscheme`
  - Added `BuildableProductRunnable` for `MarkdownApp` in Launch and Profile actions.
- Added shared ordering metadata:
  - `packages/MarkdownEngine/.swiftpm/xcode/xcshareddata/xcschemes/xcschememanagement.plist`
  - `MarkdownApp` ordered first.

## Environment Note
- Homebrew `cmark-gfm` dylibs were built with `minos 26.0`, while package target is macOS 14.0.
- This produces linker warnings but was not the primary launch blocker.
